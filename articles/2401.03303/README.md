# Управление распределением усилий в открытых программных проектах с использованием анализа фактора автобуса

## Tags
- open source software
- bus factor analysis
- software engineering
- code ownership metrics
- repository mining
- effort allocation
- developer turnover

## TL;DR
В статье исследуется расчет фактора автобуса (Bus Factor) для открытых проектов с использованием новых метрик (изменения строк кода и косинусное расстояние) вместо стандартного анализа коммитов. Авторы доказывают, что предложенный подход точнее определяет ключевых разработчиков и помогает менеджерам эффективнее распределять ресурсы.

## Краткое описание
Проекты с открытым исходным кодом сталкиваются с риском потери ключевых разработчиков, что может парализовать работу. Для оценки этого риска используется фактор автобуса (BF) — минимальное число разработчиков, уход которых приводит к остановке проекта. Большинство существующих алгоритмов опираются исключительно на количество коммитов, что не отражает реального вклада в код. 

Авторы предлагают использовать алгоритм CST с альтернативными метриками: количеством измененных строк кода (LOCC) и косинусным расстоянием изменений (change-size-cos). Исследование охватывает пять крупных высокопроизводительных вычислительных проектов на GitHub (PETSc, Spack, Hypre, Lammps, NWChem). Результаты сравниваются с подходом на основе git-blame (алгоритм RIG) и валидируются через обратную связь с главными разработчиками проектов. Анализ временных трендов за пять лет показывает, как динамика фактора автобуса может направлять процесс найма персонала и передачи знаний.

## Основные идеи
- Применение метрик LOCC и косинусного расстояния вместо коммитов для расчета фактора автобуса.
- Валидация результатов алгоритмов через прямые опросы главных разработчиков проектов.
- Сравнение коммит-ориентированного алгоритма CST и blame-ориентированного алгоритма RIG.
- Анализ фактора автобуса не только на уровне всего проекта, но и по ключевым поддиректориям.
- Исследование пятилетних трендов концентрации знаний для прогнозирования рисков текучки кадров.

## Какую проблему решает статья
- Существующие алгоритмы расчета фактора автобуса опираются на коммиты, которые игнорируют стиль разработчиков и реальный объем добавленного или удаленного кода.
- Стандартные инструменты страдают проблемами масштабируемости и не завершают работу на крупных репозиториях за разумное время.
- Отсутствие эмпирической валидации результатов автоматических расчетов фактора автобуса со стороны руководителей проектов.

## Метод
- **Подход:** Модификация алгоритма CST (Cosentino et al.) для работы с новыми метриками в составе программного фреймворка GReMCat.
- **Метрики:** Использование LOCC (количество измененных строк) и change-size-cos (косинусное расстояние между добавленными и удаленными словами в строках для оценки реального влияния изменений).
- **Базовые линии:** Оригинальный инструмент CST на базе коммитов и алгоритм RIG на базе гистограммы обвинений (git-blame).
- **Данные:** Пять открытых HPC-проектов с GitHub (PETSc, Spack, Hypre, Lammps, NWChem).
- **Очистка данных:** Удаление внешнего кода по путям директорий и объединение псевдонимов авторов с помощью библиотеки fuzzywuzzy.

## Главные результаты
- Предложенный метод (CST с LOCC и change-size-cos) показал меньшую ошибку относительно оценок главных разработчиков по сравнению с базовыми алгоритмами.
- Алгоритм RIG продемонстрировал худшую точность, высокую стохастичность (разные результаты при повторных запусках) и не смог завершить работу на крупных проектах.
- Инструменты оригинального алгоритма CST зависали на репозиториях крупного размера, тогда как реализация авторов оказалась более масштабируемой.
- Анализ по поддиректориям выявил локальные резкие падения фактора автобуса, которые невозможно заметить при оценке проекта в целом.

## Важные концепции
- **Фактор автобуса (Bus Factor):** Метрика концентрации знаний, показывающая минимальное число ключевых участников, уход которых критичен для проекта.
- **Косинусное расстояние изменений (change-size-cos):** Метод сравнения текста измененных строк, позволяющий отличать косметические правки (например, переименование переменных) от значимого изменения кода.
- **Стохастичность RIG:** Случайная выборка уходящих разработчиков в алгоритме RIG приводит к нестабильным результатам при каждом запуске.

## Ограничения
- Зависимость качества анализа от корректности очистки внешних библиотек и псевдонимов авторов в репозитории.
- Сложность получения экспертной оценки и имен ключевых разработчиков из-за политики конфиденциальности некоторых проектов.
- Порог масштабируемости для алгоритма RIG и старых инструментов анализа на репозиториях с сотнями тысяч файлов.

## Практическое применение
- Управление рисками в открытом и корпоративном программном обеспечении.
- Планирование найма новых сотрудников на основе узких мест в кодовой базе.
- Организация адресной передачи знаний (knowledge transfer) внутри инженерных команд.
- Аудит состояния безопасности долгосрочных инфраструктурных проектов.

## Итоговые выводы
- Метрики LOCC и косинусного расстояния точнее отражают вклад разработчиков в кодовую базу, чем простой подсчет коммитов.
- Алгоритм CST превосходит стохастический подход RIG по стабильности и точности.
- Мониторинг фактора автобуса по директориям во времени позволяет своевременно выявлять зоны риска.
- Предложенный подход масштабируется на крупные программные проекты лучше существующих аналогов.
