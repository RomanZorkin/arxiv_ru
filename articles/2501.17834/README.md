# Иерархическая архитектура резервного копирования для высокорискового онлайн-вывода моделей машинного обучения

## Tags
- Machine Learning
- Robustness
- Fault Tolerance
- Financial Systems
- Online Inference
- System Architecture
- Open Banking

## TL;DR
Авторы предлагают иерархическую архитектуру резервных моделей для обеспечения отказоустойчивости ML-систем в реальном времени. Метод минимизирует риски при сбоях внешних данных или инфраструктуры, обеспечивая непрерывность принятия решений в финансовом секторе.

## Краткое описание
Статья решает проблему уязвимости систем машинного обучения, работающих в режиме реального времени, к сбоям внешних API, задержкам сети и отказам инфраструктуры. В финансовой сфере, где ошибки в оценке рисков или мошенничества ведут к прямым убыткам, стандартные методы обучения не гарантируют стабильность. Предложенная иерархическая архитектура включает основную модель и несколько уровней резервных моделей (fallback models), которые активируются при недоступности определенных групп признаков или самой модели. Система также использует политики повторных попыток (retry policies) и клиентские резервные модели для критических ситуаций. Практическая значимость подтверждена кейсом компании Trustly, где архитектура успешно защищает процессы оценки транзакций при сбоях внешних провайдеров Open Banking. Главный результат — повышение надежности системы без критической потери точности в экстремальных условиях.

## Основные идеи
- Иерархическая структура резервирования для различных типов сбоев.
- Использование моделей, обученных на подмножествах признаков, при недоступности внешних данных.
- Внедрение клиентских резервных моделей (hardcoded) как последнего рубежа защиты.
- Динамические политики повторных попыток с учетом SLA и вероятности успеха.
- Выборочное резервирование на основе финансовой значимости транзакции.

## Какую проблему решает статья
- Непредсказуемые сбои внешних API (Open Banking) и инфраструктуры.
- Проблемы с латентностью (latency spikes) и таймаутами при высокой нагрузке.
- Невозможность гарантировать робастность модели на этапе обучения для всех сценариев отказа.
- Риск финансовых потерь при недоступности ML-сервиса в критических процессах.

## Метод
Архитектура состоит из трех уровней:
1. **Уровень признаков:** При недоступности внешних данных активируются модели, обученные без соответствующих групп признаков.
2. **Уровень инфраструктуры:** Реализует политики повторных попыток (retry) при временных сбоях или скачках латентности.
3. **Клиентский уровень:** Встроенная в сервер приложений упрощенная модель, работающая при полном отказе основной инфраструктуры.

Выбор резервных моделей оптимизируется для минимизации операционных затрат и максимизации покрытия сценариев сбоев. Для критических транзакций возможен параллельный вызов моделей для снижения времени отклика.

## Главные результаты
- Успешное внедрение в промышленную систему оценки рисков Trustly.
- Максимальное падение точности (PR-AUC) при переключении на резервную модель составило 9,09%.
- Падение точности при использовании жестко закодированной клиентской модели составило 58,06%, однако этот сценарий затрагивает менее 0,00001% трафика.
- Система сохраняет работоспособность при резких скачках нагрузки (например, во время спортивных событий).

## Важные концепции
- **Fallback models:** Специализированные версии моделей, обученные на ограниченных наборах данных, что делает их устойчивыми к отсутствию конкретных признаков.
- **Retry policy:** Логика принятия решений о повторном запросе, балансирующая между временем ожидания (timeout) и доступным SLA.
- **Graceful degradation:** Стратегия постепенного снижения сложности модели при невозможности выполнения основного сценария, обеспечивающая минимально приемлемый уровень сервиса.

## Ограничения
- Резервные модели неизбежно имеют более низкую точность, чем основная.
- Сложность выбора оптимального набора резервных моделей (комбинаторный рост при большом числе групп признаков).
- Необходимость ручной настройки порогов таймаутов и политик повторов.
- Высокие требования к инфраструктуре при параллельном запуске нескольких моделей.

## Практическое применение
- Финансовые технологии (оценка кредитных рисков, антифрод).
- Системы реального времени, зависящие от внешних API.
- Критически важные ML-сервисы в облачной инфраструктуре.
- Любые системы, где простой модели ведет к прямым финансовым или репутационным потерям.

## Итоговые выводы
- Иерархический подход эффективно минимизирует риски при сбоях данных.
- Резервные модели обеспечивают предсказуемость поведения системы.
- Метод позволяет поддерживать работоспособность при экстремальных нагрузках.
- Основной trade-off заключается в потере точности ради доступности сервиса.
- Будущие исследования должны сфокусироваться на автоматизации выбора резервных моделей через методы исследования операций.
